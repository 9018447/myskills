# 拆分为 Ticket

将计划、规范或对话拆分为一组 **ticket**——tracer-bullet 垂直切片，每个都声明阻塞它的其他 ticket。

Issue 跟踪器和分类标签词汇表应已提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文中已有的内容开始。如果用户传入引用（规范路径、Issue 编号或 URL）作为参数，获取它并读取其完整正文和评论。

### 2. 探索代码库（可选）

如果你尚未探索代码库，请先了解代码的当前状态。Ticket 标题和描述应使用项目的领域术语表词汇，并尊重你正在接触的区域的 ADR。

**用 ast-grep 与影响面分析把边和范围定准，不靠猜。** 阻塞边和改动范围写错，直接污染 `/acpxtodo` 的波次调度（漏边=并发票互相踩，多边=白白串行）。起草前对计划要触碰的核心符号做两件事：

- **`/gitnexus-impact-analysis`（或 CLI `impact <symbol> -d upstream --repo .`）**：对每个计划改动的共享符号查上游影响面。改动票 A 的符号被票 B 的实现读到 → B 必须被 A 阻塞；影响面里没有任何其他票的符号 → 不加边。d=1 直接依赖 WILL BREAK、d=2 LIKELY AFFECTED 的分级照用。
- **ast-grep**：按语法形态（调用点、类型引用）核实两票的改动是否会落到同一符号/同一文件——文本 grep 容易把同名不同物算重叠。相交的票要么合并、要么显式加边串行。

影响面为空不等于安全：GitNexus 索引没解析到的符号（动态派发、跨语言调用）会返回空，先用 `zg --rg` 复核再下结论。

**边与相交的最终确认走 `/jev`**：把上面收集的证据整理进 `state`，将"票 B 是否真的读取票 A 改动的符号""两票相交是否语义性（合并/加边）""这条边是否可删"等判定题一次性批量提交 jev；低置信度或 escalate 的自己回代码复核。jev 结论是判定辅助，不是授权边界——最终拆解仍由用户在下一步批准。

寻找预重构代码的机会，使实现更简单。"让改动变得容易，然后再做容易的改动。"

### 3. 起草垂直切片

将工作拆分为 **tracer bullet** ticket。

<vertical-slice-rules>

- 每个切片在每个层面（schema、API、UI、测试）提供一条狭窄但**完整**的通路——垂直，而非某个层面的水平切片
- 一个完成的切片本身是可演示或可验证的
- 每个切片要小,以适合单个全新的上下文窗口(128-256 K tokens)
- 任何预重构应首先完成

</vertical-slice-rules>

为每个 ticket 指定其**阻塞边（blocking edges）**——必须先完成才能开始的其他 ticket。没有阻塞项的 ticket 可以立即开始。

**依赖图宽而浅，并发才大。** 本技能的产出默认由 `/acpxtodo` 按 worktree 波次并发执行：每轮取所有前置票已完成的票同时派发，依赖边的数量直接决定每波就绪集的大小。只给真正的数据/接口依赖加边——"顺手"、"逻辑上相关"不构成阻塞边；能并行的票不要用边串成链。反过来，两票若会改同一个文件且语义相交（如同一个 reducer 的两个分支），要么合并成一票，要么接受它们将在 merge-back 暴露冲突、显式加边串行——用下面的**改动范围**字段自查。

**时长不可控的真实运行是垂直切片的例外。** **运行票**是验收标准里含时长不可控或批量的真实运行(真实模型回归、真实语料批量扫描)的 ticket。它不能与实现工作同票:一次 agent 派发有时间上限,实现+真实运行的总时长必然超限(实测:回归票在 1 小时处被强制中断,被迫现场考古续作)。凡验收标准需要此类运行的,拆成两张:代码票只做离线可验证的实现,被**运行票**阻塞——运行票实现成分最小化(runner 脚本或命令序列),交付内容是记录数字的报告,验收标准是数字门槛。分钟级、结果确定的真实验证(挂一次服务验证旗标生效)不算此类,留在代码票里。

**大范围重构是垂直切片的例外。** **大范围重构**是一种机械性变更（如重命名列、更改共享符号类型），其**影响范围**波及整个代码库，一次编辑会同时破坏数千个调用点，导致没有垂直切片能保持绿色。不要强行塞进 tracer bullet；而是通过**扩展-收缩（expand-contract）**来序列化。首先扩展：在旧形式旁边添加新形式，确保没有任何东西被破坏。然后按影响范围大小分批迁移调用点（按包、按目录），每批作为自己的 ticket，被扩展阻塞，由于旧形式仍然存在，CI 在批次之间保持绿色。最后收缩：在所有调用者迁移完毕后删除旧形式，作为一个被所有迁移批次阻塞的 ticket。即使当批次本身无法单独保持绿色时，保留这个序列，但让它们共享一个集成分支，该分支最终阻塞一个集成-验证 ticket——绿色只在那里承诺。

### 4. 征求用户意见

以编号列表的形式展示提议的拆解方案。对每个 ticket，展示：

- **标题**：简短描述性名称
- **被以下阻塞**：哪些其他 ticket（如果有）必须先完成
- **改动范围**：预计会改动的目录/模块级路径（如 `manager/src/`、`agent/src/bridge.jl`）——到目录或单文件即可，不要求精确到行。这是 `/acpxtodo` worktree 并发时预测 merge-back 冲突的输入
- **交付内容**：此 ticket 使哪个端到端行为生效
- **运行预算**：离线，还是含真实运行——含真实运行的票是否已与实现拆开

询问用户：

- 粒度是否合适？（太粗 / 太细）
- 阻塞边是否正确——每个 ticket 是否只依赖真正制约它的 ticket？
- 是否有任何 ticket 需要合并或进一步拆分？

迭代直到用户批准拆解方案。

### 5. 将 ticket 发布到已配置的跟踪器

发布已批准的 ticket。**发布方式**取决于 `/setup-matt-pocock-skills` 配置的跟踪器——ticket 本身相同，只有阻塞边的形式不同：

- **本地文件** → 在 `.scratch/<feature>/issues/` 下为每个 ticket 写入一个文件，按编号顺序命名（`01-<slug>.md`、`02-<slug>.md` 等），阻塞项在前。每个 ticket 的顶部通过 `Blocked by:` 行列出其依赖的标题。使用下面的文件模板。
- **真实 Issue 跟踪器（GitHub、Linear 等）** → 按依赖顺序每 ticket 发布一个 Issue（阻塞项在前），这样每个 ticket 的阻塞边可以引用真实标识符。在平台支持的地方使用原生阻塞/子 Issue 关系；否则在每个 ticket 的 "Blocked by" 中设置阻塞的 Issue。除非另有指示，应用 `ready-for-agent` 分类标签——这些 ticket 本身就是 Agent 可抓取的。

不要关闭或修改任何父 Issue。

无论哪种形式，避免在正文里写精确到行的文件路径或代码片段——它们很快就会过时。**改动范围**字段是唯一例外：目录/模块级的路径是给 `/acpxtodo` 预测 merge-back 冲突用的，必须写。其余例外：如果原型产出的代码片段比文字更精确地编码了某个决策（状态机、reducer、schema、类型结构），将其内联并简要说明来自原型。精简到决策密集的部分——不是工作演示，只是重要的内容。
