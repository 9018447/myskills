# To Tickets（拆分为工单）

把计划、规格说明或对话拆分成一组**工单**：曳光弹式的垂直切片，每个工单声明哪些工单**阻塞**它。

issue 跟踪器和分诊（triage）标签词表应当已经提供给你。如果没有，请用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话中已有的内容开展工作。如果大臣传入了引用（规格说明路径、issue 编号或 URL）作为参数，获取并阅读其完整正文和评论。

寻找可以预重构（prefactor）代码的机会，让实现更容易。"先让改动变容易，再做容易的改动。"

### 3. 起草垂直切片

把工作拆分成若干**曳光弹**工单。

<vertical-slice-rules>

- 每个切片窄而**完整地**贯穿所有层（schema、API、UI、测试）：纵向切穿，而不是只切某一层的水平切片
- 完成的切片自身可演示或可验证
- 每个切片的规模应能放进一个全新的上下文窗口
- 预重构工作应先于切片完成

</vertical-slice-rules>

为每个工单指定其**阻塞依赖边**：必须在它开始前完成的其他工单。没有被阻塞的工单可以立即开始。

**大范围重构是垂直切片的例外。** **大范围重构（wide refactor）**指一次机械式改动（重命名一个字段、更换共享符号的类型），其**爆炸半径**波及整个代码库，一次编辑会同时打断上千处调用点，任何垂直切片都无法单独保持 CI 绿灯。不要硬把它塞进一发曳光弹；按 **expand–contract（扩展–收缩）** 排序：先扩展——在旧形式旁边加入新形式，什么都不破坏。然后按爆炸半径分批迁移调用点（按包、按目录），每批各自成单，被扩展步骤阻塞；因为旧形式仍然存在，批次之间 CI 始终保持绿灯。最后收缩——当不再有调用者引用旧形式时删除它，该工单被所有迁移批次阻塞。如果连单批都无法各自保持绿灯，仍保留这个序列，但让各批共用一个集成分支，并且全部阻塞最后一张"集成并验证"工单；绿灯只在那一张工单上承诺。

- 切片不应该太细，目前的模型至少有`256 K`上下文窗口，甚至有`1M`上下文。 可以把一大部分作为一张tickets.
- tickets 是实际的编码工作，应该都能被**测试驱动开发** 执行，如果是前置或后置工作：文件整理，数据整理，信息收集等。以文件的形式落档在系统，然后报告大臣，而不是加入票中。
- 不要硬凑tickets. 每一步执行本身都包含了TDD和code review. 因此测试不应该包含在票工作中。票只为需求服务。
- tickets是人类可读的，可以写English，但是票不应该存在意义不明的黑话和行话。写清楚要求与目的。语言应尽可能的详实，让人类读起来像在读散文。
- 
  🔴反例： 
   - 写太过专业或意义不明的黑话
   - 人类根本读不懂的tickets
   - 把tickets 拆的太细或不可分需要多次循环，浪费时间。
   - 单独一张tickets作为测试
   - 把非编码工作作为tickets


### 4. 发布工单到已配置的跟踪器

写好票直接发布工单，**发布方式**取决于 `/setup-matt-pocock-skills` 配置的跟踪器；两种模式下工单内容相同，只是阻塞依赖边的形态不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每个工单写一个文件，按依赖顺序从 `01` 开始编号（阻塞者在前）。每个文件的 "Blocked by" 列出它依赖的编号/标题。使用下方的单工单文件模板：一文件一工单，绝不要写成单个合并文件。
- **真实 issue 跟踪器（GitHub、Linear 等）** → 按依赖顺序（阻塞者在前）每个工单发布一个 issue，以便每张工单的阻塞依赖边能引用真实标识符。平台若有原生阻塞关系就使用它；否则把每张工单的 "Blocked by" 设为对应的阻塞 issue。若来源是一个已有 issue，则把每张工单建为它的子 issue（见跟踪器文档的操作说明）。除非另有指示，统一打上 `ready-for-agent` 分诊标签；工单在设计上即为 Agent 可直接领取。

按**前沿（frontier）**推进：任何阻塞者已全部完成的工单都可以做。对纯线性链而言，就是从前往后依次执行。

不要关闭或修改任何父 issue。
