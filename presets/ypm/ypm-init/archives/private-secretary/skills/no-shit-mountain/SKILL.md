# No Shit Mountain · 四关检查

对当前更改过一遍四关，每关给出 🟢🟡🔴 结论和 file:line 证据。四关全绿才算通过；任何一关红灯，改动不得验收或合入。

## 范围

用调用方指定的文件或 diff；否则用对 base 分支（默认 `main`）的当前 diff，含工作区新增的未跟踪文件。每一份改动文件都要过每一关，一份不漏。

## 第一关 · 注释

标准来自 `/no-comments`：应用代码里的注释都是发现，只有约束注释可以留下——`do not remove` / `do not change wording` / `talk to X before changing`，以及 ponytail 的 `shortcut: 限制, 升级时机`——且必须真能说清"为什么这行代码改不动它"。rg 扫改动文件里的注释行，逐条判定：删除，还是给出留下理由。

完成标准：改动里每一行非约束注释都有了处理结论。

## 第二关 · 重复

对每份新增文件：先用一句话提炼它的核心职责，再 rg 搜现有代码里同职责的实现（关键函数名、字符串、逻辑特征）。三选一：

- **重复**：现有文件已做这件事 → 新文件该删，改用现有实现；
- **该迭代**：和现有文件是同一件事的新版本 → 应在原文件上改，而不是新增；
- **新增合理**：现有代码确实没有 → 附上搜过什么关键词的证据。

完成标准：每份新增文件都有结论，"新增合理"必须附搜索证据。

## 第三关 · 归属

对每份新增或移动的文件问：它的上级目录是不是它功能的归属地？两个检验：同目录的邻居和这份文件是不是同一类东西；一个要改这个功能的开发者顺着目录结构找，会不会走到这里。目录成了杂物抽屉（什么都往里放）或文件放错了家族，都是 🔴，给出应去的位置。

完成标准：每份新增/移动文件都有归属结论；说不出归属理由的按错位处理。

## 第四关 · ponytail

完整教义见 `/ponytail` skill，这里是最容易失守的检查点，逐条回答：

- 每个新增文件、能力都是任务要的？没人要的功能、选项、配置、"以后再说"的抽象 = 🔴，点名删除；
- codebase 已有的 helper、组件、模式，用上了没有？还是又写了一份；
- 非平凡新逻辑（分支、循环、解析、钱、安全）带测试或 assert 自检没有；
- 已知限制标了 `shortcut:` 没有。

完成标准：四条各有明确答案，不是"大概没问题"。

## 报告

一表交出：关卡 / 结论 / 证据（file:line）。只写问题报告，不做解决方案
