### Bug 修复

讲科学。交付的每一行都要能追溯到运行时证据。“也许有用”这种双保险只是假设，不是修复——不许交付。当证据否证了某个假设，就回滚由它驱动的那部分改动。只交付证据支撑下的最小改动，不多不少。

1. 亲自在对应的操作界面上复现，走控制技能（参见共享策略中的运行时验证规则），即便调试或埋点协议建议让用户复现，也照样自己上手。只有当你已把控制界面推至能力边界，仍能列出一条明确、具体的理由说明它无法触达目标时，才向用户求助。若无法直接复现，就合成触发条件、收紧环境、加埋点，直到它响为止。
2. 对成因做二分。列出候选假设，逐一排除，直到只剩一个存活。用 `how` 覆盖受影响的子系统，用 **why** 技能拉取回归历史，作为假设的种子。每一轮，选能砍掉最多剩余问题空间的划分，取运行时证据、做排除。程序状态不清时，加埋点或日志，在代码运行时读出来。别猜。漫长或顽固的追查，用当前可用的、经验证的循环或 watcher 机制推进。
3. 规划修复。先使用`to-spec`建立规划spec,然后使用`implement`修复
4. 在同一界面上验证。原始复现现在通过。“Inconclusive”（结果不定）或在错误界面上的通过，都不算通过——要标出来。单元测试只能说明分支行为，不能证明 bug 不存在。
5. 编排提交，让失败的复现在 git 历史中落在修复之前。当该 bug 有便宜的本地测试路径时，按 **tdd** 技能的“失败测试先行”节奏走。若测试昂贵、依赖重度集成或难以写清，就跳过。
   这就是标准的 **principle-sequence-verifiable-units** 技能——失败测试在下，修复在上。
6. 执行 **Opening a PR**。

**回复：** 坏了什么、根因、修复、如何验证。逐字贴上“先失败后通过”的复现输出。
