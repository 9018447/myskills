# 用测试驱动 Julia 科学计算改动

遵守 [YPM 共享规则](../../../references/ypm-policy.md)。默认使用 `Test` 和 `Pkg.test()`，沿用项目声明的 Julia 版本和测试体系。参考示例以 Julia 1.11 为基线。

## 1. 确定契约并运行基线

阅读相关实现、测试、`Project.toml` 和 CI 测试入口。确认输入单位、有效范围、公开接口、测试依赖和运行命令。

为当前行为写下输入、正确性依据、验收条件和无解或非法输入的处理方式。数值契约须给出残差定义、尺度和容差来源。优先使用解析解、独立参考值或适用的数学与物理性质。不得用待测函数生成自己的期望值。

运行受影响的现有测试，区分已有失败与本次失败。缺少环境时先修复环境；无法恢复时报告未验证项，不把环境错误当作 Red。

按任务选择入口：

- 新功能：从一个最小正确案例开始，逐轮补边界与异常。
- Bug：固定触发输入，先得到能重现缺陷的回归测试。
- 纯重构：先确认旧行为基线通过，不强求新增失败测试。
- 求解器改进：先规定残差、可行域和收敛状态，再加入典型、极限与困难案例。成功状态不能代替解的正确性。

## 2. Red：运行一个会因目标行为失败的测试

一次测试一个可观察行为。运行新测试，记录命令、失败断言和实际结果。语法错误、缺少依赖和加载失败不算有效 Red。

若新测试已通过，检查缺陷是否已消失、输入是否能触发问题、断言是否区分正确与错误行为。确认原因后再决定是否修改生产代码。

包测试优先进入既有测试入口。独立脚本项目可使用可重复运行的测试脚本；不要为满足形式搭建包或脆弱 Mock。

## 3. Green：只实现当前契约

修改使当前测试通过所需的最少生产代码，再运行同一个测试。不要为通过而放宽容差、删除断言、硬编码样例答案或增加 `broken`、`skip`。

若契约有误，先用独立依据纠正契约并记录原因，再修改测试。若尚无可信正确性依据，先调查或做实验；不得把当前输出直接固化为正确答案。

## 4. Refactor：在通过后整理实现

整理命名、重复逻辑、数据流和热路径，每次小改后重跑相关测试。数值核心优先使用显式输入和返回值。

守住精度与物理契约。除非外部接口明确要求，不固定末位浮点值、迭代次数或算法路径。当前行为稳定后再进入下一轮 Red。

需要浮点断言、随机输入、测试环境配置或示例时，读取 [数值测试参考](TDD-Julia-Playbook.md)。按实际风险选择检查，不强制每项任务覆盖所有物理性质。

## 5. 验证并交付

依次运行定向测试、受影响的相邻测试和完整包测试；脚本项目运行完整脚本测试入口。确认测试纳入正式入口，且不依赖执行顺序或其他测试的随机状态。

数值任务除参考值外，按适用性验证有限值、残差、守恒与可行域。涉及性能目标时，先验证正确性，再预热并测量稳态性能。

仅有“没有异常”“返回数组”“求解器成功”或“与旧代码一致”不足以证明正确。全量测试已有失败时，报告失败范围及与本次变更的关系，不宣称全绿。

完成 [Opening a PR](../ypm-playbook-opening-a-pr/SKILL.md) 的适用步骤，遵守现有提交、发布与合并授权。

交付时说明改动行为、Red 证据或重构基线、实际验证命令及结果、未验证的风险。未运行的检查明确写为未运行。
