用户请求了**回顾复盘**。你要做的是针对编码 agent 的**运行环境**提出改进建议，让之后的会话跑得更好。

## 步骤

1. 调用 Skill 工具加载 `writing-for-agents`，获取写作风格指南。

2. 阅读用户指定的那次会话的一手资料。这可能需要在本机上翻找会话日志；如果用户没有指定会话，默认复盘当前会话。

3. 在以下类别中寻找改进候选。

- **导航**：agent 找到正确文件有多容易？文件之间有没有隐藏依赖？加一个**导航指针**（指向关键文件的一句话说明）会不会更省事？_何时使用_：会话花了很长时间才找到某条信息。
- **自动化检查**：有没有能抓住 agent 所犯错误的自动化检查？Lint、类型检查、测试、文件系统 linter？先读仓库自己的检查命令（它的 `package.json`/构建工具的 `lint`/`check` 脚本、CI workflow），这样"检查已经存在但没接上或悄悄坏了"本身就是一条发现，而不是重复造一个。一个没有任何**护栏**的仓库（既没有 pre-commit 钩子，也没有跑 lint/类型检查/测试的 CI 任务）本身就是一条发现：没有 lint 的仓库是一个持续错失的机会，不是中性默认。_何时使用_：agent 犯了一个自动化检查本可以抓住的错误，或仓库完全没有护栏。
- **编码规范**：应该给**审查 agent** 新增一条要执行的规则吗？应该删除或澄清某条现有规则吗？先给违规分类：**机械性**违规（固定的句法模式、被禁的 API、import 形态、文件位置规则）一律配确定性检查——在仓库自己的 linter 里加自定义规则、加新 pre-commit 钩子、或加新 CI 任务，按仓库的语言和现有护栏选最便宜的那种。默认做检查而不是写规则。`CODING_STANDARDS.md` 只留给真正的**判断题**（跨文件一致性、"与周围风格一致"，以及任何护栏都替代不了的东西）。_何时使用_：审查 agent 没能抓住某个错误。
- **全局 AGENTS.md**：有没有引导指令其实应该移到编码规范（或自动化检查）里？_何时使用_：AGENTS.md 文件特别大——仓库里的或用户全局范围的。
- **工具经济**：agent 有没有做出本可精简的昂贵工具调用？有没有特别浪费 token 的自定义工具（CLI、MCP）？_何时使用_：agent 做出了昂贵的工具调用。
- **无操作指令**：找出引导文件里那些并不改变 agent 行为的指令。_何时使用_：引导文件又大又难维护。
- **信息访问**：寻找增加 agent 信息获取机会的手段。例如把 dev server 日志 tee 出来、给第三方服务开只读访问。_何时使用_：某条关键信息 agent 当时拿不到。

4. 按严重程度从高到低排序，把这些候选呈现给用户。

## 参考

### 实现与审查

记住所有工作都分两个阶段：实现和审查。实现 agent 承受最大的**上下文压力**：它负责探索、写代码、调试失败。

审查 agent 的上下文压力最小——它拿到的是 diff，不需要探索，通常也不用写代码、不用调试。

所以执行编码规范的职责应该放在审查 agent 身上，而不是实现 agent。

### 文件

你可以使用仓库里的这些文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推进任何在这个仓库工作的 agent 的上下文窗口。要极度节省地用，通常只放指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：这个文件在审查阶段读，不在实现阶段读。如果它超过 1,000 行，就加指向 docs 文件夹的**导航指针**。
- 文档（Docs）：把文档当参考资料用，由其他文件指向。写新文档前先找已有的。
- 技能（Skills）：文档做成技能来用（因为技能的 description 会进入 agent 的上下文窗口），或者用于用户主动调用的命令。遵循 `writing-for-agents` 技能里的建议。
