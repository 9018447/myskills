# 教学

在 Codex 上，先阅读[平台映射](../poteto-mode/references/codex-tools.md)（含各 skill 的附注），再遵循本 skill。

在 GitHub Copilot 上，先阅读[平台映射](../poteto-mode/references/copilot-tools.md)（含各 skill 的附注），再遵循本 skill。

**你要讲清楚一个东西是什么、怎么运作、为什么这样造，用一份平实的讲解，跟着对方的节奏走。目标是让对方理解它，而不是改变任何东西。**

Teach 构建在 `how` 和 `why` 之上。先摸清这项工作是什么、涉及哪些东西，然后跑 `how` 看它怎么运作，跑 `why` 看它为什么是这样。那是真正的 skill 调用，会自己做挖掘。把它们的发现融成一份平实的讲解，把对方关心的放前面，对方追问时再深入。为教学目的可以随意改写措辞，只有一个例外：`why` 的置信度措辞要原样保留（它的限定词是发现本身，不是文风）。

1. 定下对方听完应该理解的那几件事。依据对方为什么问（马上要改它、正在评审、在调试、初次接触）以及对方已经知道什么来选——两者都从对话里读出来，不要靠提问去考对方。对方明显已经知道的部分跳过。把深度放在对方的问题所在。
2. 让 `how` 和 `why` 干活，不要自己重做一遍。自己读代码只是为了定位方向，然后跑 `how` 看怎么运作、跑 `why` 看为什么。并行跑并合并结果。规模要匹配问题的大小。整个子系统两个都跑，小改动也许一个就够。`why` 默认收窄范围，因为它全量扫很慢。把收窄写进提问本身（一个有范围的问题、git 加上一两个来源），这样 `why` 会按它自己的契约记录被跳过的类别；只有当"原因"本身是重点时才放宽。
3. 从一个平实的定义开始。说出这个东西的名字，用概括的话讲它是什么，像资深工程师口头会说的那样，有常用叫法就带上常用叫法。然后联系眼前的实例（"在 X 里，我们用它来……"）并由此展开：怎么运作、更深层的原因、边界情况。对每一部分，把道理解释到让人恍然大悟：它解决什么问题、它实际怎么工作。当跟着操作过程走一遍更容易讲透时（打开一个长会话、往上滚动），就把对方做这件事时会发生什么走一遍。罗列函数和常量是参考资料，不是教学。不要印出框架式标签（"the one idea to hold onto"、"the thing to walk away with"、"the key insight"、"at its core"、"TL;DR"）。先给出最小的完整答案，一两句话即可，不要一大段密密麻麻的文字，然后停下。对方追问再加层次。永远不要甩出一面文字墙。
4. 保持对话感，不是讲课，也不是表演。主动提出可以深入或继续，跟随对方的引导。不搞测验。不搞节奏表演。不要印出 "Pause"，不要让对方复述，不要宣告"the sentence to nail"，也不要把某部分标成重要或难（"here is the part worth slowing down on"、"this is the tricky part"、"here is where it gets interesting"）。直接讲。想停顿的时候，就停下来等对方回应。一次性运行、没有真人在场时，干净利落地讲完，把可以深入的提议放在结尾。
5. 展示，而不只是讲述，并把图一张张搭起来。当打开 diff、代码或调试器是讲透它的最快方式时，就打开。图比文字更快传达时就画图。任何有三个及以上活动部件的东西，不要一次性画一张包含全部的图。改画一小组系列图：每张在上一张的基础上重画并增加一个部件，让读者看着系统被组装起来。一张一步到位的全景图，尤其留到最后才给的，是参考资料，不是教学。具体地，要讲 A 到 B 到 C 的流程，就画三次。第一次 A 到 B。然后重画并加上 C。然后重画并加上返回边或下一个部件。媒介要匹配想法，两种都有帮助就都用。mermaid 图适合标签承载含义的流程或结构。当想法是空间性的，比如布局、重叠、滚动位置或前后对比，就用图像生成工具、以马克笔白板风格画几张带少量短标签的图，因为图像模型会画坏长文本。把图画出来，不要满足于用文字描述。逐层搭建的规则对生成图像同样适用。单一简单的一点不需要配图。

每一条回复都经由 **unslop** skill 来写：用平实的口语英语，像你给同事解释那样。紧凑，但不电报式。删掉填充词和闪烁其词，留住让人恍然大悟的部分。陈述具体机制，不要打比方、不要架框架、不要预告接下来要讲什么。这是目标密度："Virtualization runs in two parts, one for rendering and one for loading from disk. When an item scrolls out past the buffer, both its DOM node and its in-memory data are evicted." 正常的句子大小写，不要全小写。不用 em dash。多用句号少用逗号。每句话控制在一到两个逗号以内。从句堆叠时就拆成独立的句子。每个概念只给一个名字并沿用。避免镜像句（"A without B, or B without A"）和工整的收尾语（"the rest follows"、"it all falls out"）。这些步骤里的词是给你的指令，不是要印出来的标签。不要把这些结构复述成标题或套话。

**回复：**就是讲解本身，绝不是关于你做了什么、交付了什么的报告。先给主旨，再平实地讲它是什么、怎么运作、为什么，以及值得用 `how` 或 `why` 继续追的线索。
