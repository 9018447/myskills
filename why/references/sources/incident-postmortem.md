# 事故与事后复盘背景

它不是一个独立来源，而是一个**横切视角**。事故常常是防御性代码的动因（“X 故障之后我们加了这个检查”），所以当目标看起来具有防御性时（空值检查、重试逻辑、超时处理、限流、功能开关），要在每个可用来源里专门搜寻事故历史：

- **Notion**：搜索提到目标文件、功能或错误字符串的事后复盘
- **Linear**：查找带有 `incident`、`sev-*`、`postmortem-action-item`、`reliability` 标签的工单
- **Slack**：在目标代码加入日期前后搜索 `#sev-*` 和 `#incident-*` 频道
- **Git**：message 写着 “fix for incident”“add defensive check” 这类内容，或 “revert” 之后跟着 “re-apply with...” 的 commit 是强信号
- **Datadog**：用 `search_datadog_incidents` 找带时间线的正式事故记录，以及作为事后复盘行动项创建的仪表盘和监控器
- **Sentry**：first-seen/last-seen 窗口与目标 PR 上线日期吻合的 issue，以及经过目标代码的堆栈跟踪
- **Databricks**：对错误情形分类的产品分析事件（客户端上报的失败、用户可见的重试事件等）常常在事故窗口内飙升。目标 PR 上线后该事件计数下降，是“目标代码解决了用户可见症状”的旁证——即便 Datadog/Sentry 的信号很嘈杂时也是如此。

一旦发现事故关联，就把完整的事后复盘取回来。事后复盘通常有一节“行动项”，直接对应代码改动。当多个来源相互印证时（一个 Datadog 事故 ID 出现在某个 Linear 工单里，该工单又出现在某篇 Notion 事后复盘中，复盘又出现在链接到目标 PR 的 Slack 讨论串里，且修复之后 Databricks 错误事件计数下降），证据就格外有力。

当代码的防御性特征使“因事故而生”的来历显得可信时，值得花时间。对看起来不具防御性的代码，跳过即可。
