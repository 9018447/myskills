# Writing for Agents

用于编写 Skill、`AGENTS.md`、`CLAUDE.md`、Spec、Prompt、README 等智能体文档。

如果目标本身是 Skill，同时读取 `SKILL-MECHANICS.md`。

## 核心原则

智能体文档的目标不是让 Agent 每次产生相同输出，而是让它在相同条件下采用稳定、可验证的工作方法。

抓主要矛盾, 分清次要矛盾,先形成正确认识，再写精确指令。

不要把未经调查的经验、偏好或“最佳实践”直接写成硬约束。错误的精确规则比模糊规则更危险。

编写前先确认：

```text
实际目标
→ 已知事实
→ 未知问题
→ 当前主要矛盾
→ 真正决定结果的约束
→ 验证方法
```

与主要问题无关的规则，删除、后置或降为参考。

## 写具体指令

不要写愿望、评价或抽象原则，要写 Agent 可以直接执行的行为。

坏：

```text
保证代码质量。
不要过度设计。
检查实现是否正确。
```

好：

```text
运行 pnpm run check；失败时不得交付。

只修改当前 Ticket 要求的行为，不新增 Ticket 未要求的抽象层。

逐条对照 Ticket 验收项，并检查对应 diff 和测试结果。
```

每条重要指令应尽量明确：

```text
做什么
在什么条件下做
做到什么程度
如何验证
```

同时每次都应告知:

```text
实践是检验真理的唯一标准
```

Skill 中的规则、流程和判断是否正确，最终以实际执行结果检验

## 区分规则类型

不要把所有内容都写成“必须”。

* **Fact**：已经调查确认的事实。
* **Invariant**：违反后任务即错误的硬约束。
* **Default**：当前条件下的默认做法，可被更具体事实推翻。
* **Unknown**：尚未确认的事实，应告诉 Agent 如何调查，不要替它猜。

例如：

```text
Fact:
项目使用 pnpm。

Invariant:
不得修改 public API。

Default:
优先复用现有模块，不主动新增抽象层。

Unknown:
先检查 package.json，确认项目实际测试入口。
```

## 定义流程，不预设答案

复杂任务应规定认识和验证过程，而不是提前写死解决方案。

例如调试：

```text
确认现象
→ 调查事实
→ 建立可证伪假设
→ 做最小但有判别力的验证
→ 根据结果修正判断
→ 实现
→ 再验证
```

固定的是方法，不是机械步骤。

实践结果如果推翻原假设，应修改判断，不得为了服从文档继续执行错误规则。

## 按执行顺序写

流程型文档按 Agent 实际执行顺序排列。

不要按“重要程度”堆规则。

```text
读取上下文
→ 调查现状
→ 执行
→ 验证
→ 交付
```

后续步骤如果可能诱使 Agent 提前行动，不要过早展开。

## 定义完成条件

不要只写“调查”“检查”“完成”。

坏：

```text
调查现有实现。
```

好：

```text
找到行为入口、核心调用链和现有测试后，调查结束。
```

坏：

```text
验证修改。
```

好：

```text
相关测试通过，且每个修改文件都能对应当前需求后，验证完成。
```

完成条件必须能够被 Agent 自己观察。

## 精确，但不要伪精确

只有存在实际依据时才写数字约束。

坏：

```text
每个函数不得超过 20 行。
```

除非 20 行本身就是项目真实要求。

不要为了“具体”制造没有事实依据的数字。

## 控制上下文

高频、关键、执行时必须知道的内容放主文档。

低频、详细、只在特定情况使用的内容拆到 reference，并明确说明什么时候读取。

不要为了完整性把所有知识永久塞进上下文。

如果 Agent 每次都必须读取某份 reference，通常应该直接内联。

## 权限和停止条件

高风险文档必须明确：

```text
允许做什么
禁止做什么
什么时候停止
什么情况必须交给用户决定
```

不要写“谨慎处理”“酌情修改”之类无法执行的边界。

## 实践检验

文档不是不可修改的真理。

```text
规则
→ 执行
→ 实际结果
→ 比较预期
→ 修正认识
→ 修正规则
```

如果 Agent 经常偏离，不要立即增加更多文字。先判断：

```text
规则是否不具体？
规则是否互相冲突？
是否缺少关键事实？
是否约束了次要问题，却没抓住主要矛盾？
规则本身是否错误？
```

## 最终检查

交付前确认：

```text
[ ] 真实目标明确
[ ] 主要失败模式明确
[ ] 没有把猜测写成事实
[ ] 硬约束和默认规则已区分
[ ] 指令具体且可执行
[ ] 按实际执行顺序排列
[ ] 关键步骤有完成条件
[ ] 有验证方法
[ ] 权限和停止条件明确
[ ] 没有无关规则堆积
[ ] 新的实践证据可以修正旧规则
```

判断文档好坏，以 Agent 实际行为为准，而不是以文档长度或形式完整性为准。
